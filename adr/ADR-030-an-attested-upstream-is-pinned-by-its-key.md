# ADR-030: An Attested Upstream Is Pinned by Its Key at the Connection, Not Labelled in the Verdict

**Status:** Proposed
**Date:** 2026-10-19
**Authors:** MCP Hangar Team

## Context

State of `main` on 2026-10-19: core 2.31.0 (`40f448a1`), operator `6d5d7e6` with CRD `v1alpha2`.

**Hangar already proves the integrity of a tool's contract, and nothing about the code behind it.** The JCS digest over `{name, description, inputSchema, outputSchema}` ([ADR-004](ADR-004-sep-1766-digest-pinning.md), `domain/services/digest_validator.py`) is enforced by `_gate_digest_pin` and `_gate_deferred_digest_pin` (`server/tools/batch/executor.py:2234`, `_GATES` at `:3104-3117`). **External forces.** Attestation of MCP servers is being named as a gap by the confidential-computing community, and TEE-hosted MCP gateways now position themselves against software-only governance: a policy engine inside a TEE with its policy hash in the attestation report, without a fleet, Kubernetes or contract digests. Research on MCP security shows that an MCP server an intermediary cannot authenticate is easy to impersonate.

**Boundaries this record does not move.** Deterministic enforcement, no ML; no SaaS ([ADR-010](ADR-010-retire-agent-cloud-tier.md)); L7 egress with a network backstop and no MITM/eBPF ([ADR-013](ADR-013-egress-policy-enforcement-model.md)); in-cluster MITM outside the threat model; the event log signed by the operator's key (the circular trust named in docs#252) stays as it is.

**The question.** Whether, where and in what form the fact "this upstream runs attested code" enters Hangar's behaviour — and what Hangar must refuse to become in the process.

## Decision

When an operator declares an upstream `tls.attested: true`, Hangar requires every connection that carries traffic to that upstream to terminate at a key whose SPKI digest is in the operator's pin list — keys the operator obtained from a Key Broker Service that releases them only to attested guests — verified inside the TLS handshake and before the first byte, and recorded in the audit trail from the socket. Hangar does not verify evidence, trust a CA, issue nonces, or become a subject of attestation, and "attested" means attestation-gated issuance (Guarantee A), never continuous runtime attestation (Guarantee B).

### 1. Two independent policy enforcement points; Hangar is the first and only the first

Hangar answers `allow(principal, tenant, tool, args)`. A Key Broker Service (Trustee KBS or equivalent) answers `release(secret, measurement, nonce, pubkey, policy)` to an attested guest. Neither replaces the other: a Hangar refusal means the call never reaches the upstream; a KBS refusal means the upstream has nothing to execute it with. Hangar does not hold downstream secrets, does not release keys and does not become a KBS.

### 2. The attestation-derived fact Hangar consumes is the public key at the other end of the connection

An attested upstream terminates TLS with a per-workload leaf key that the KBS released to that guest after attestation. Hangar pins the SPKI digest of that key (`peer_identity.spki_sha256`, a list to allow rotation windows). No CA is a trust input for an attested server: a CA private key released to a guest would let any admitted guest mint a certificate for any name, a CA kept at the issuer still makes the SAN a statement of issuance policy Hangar cannot see, and hostname matching in the client accepts DNS/IP SANs only, so a SPIFFE URI SAN would not survive the handshake and a static leaf cannot carry a CNI-assigned pod IP. Pinning the key removes all three problems: the chain is irrelevant (a self-signed leaf is fine), the name is irrelevant, and what Hangar records is *this connection terminated at key K, which the operator obtained from the KBS resource provisioned for this workload*. That resource is named in the declaration as `peer_identity.key_ref` (for example the KBS resource path), a stable name for the key lineage that does not change when the key rotates (§7). The binding holds for the life of the connection; Hangar does no TTL, nonce or replay reasoning.

This record assumes the key pair is provisioned as a KBS resource before the workload starts, so the operator knows its SPKI before the pod exists and reads it from that resource. A key generated inside the guest qualifies only if the guest registers its public key with the KBS as part of attestation and the operator reads the SPKI from the KBS; an SPKI read from the running pod never qualifies, because that pins whatever answered.

Two guarantees are kept apart and this record provides only the first. **Guarantee A — attestation-gated credential issuance:** key K was released under a policy that required a successful attestation of the guest for the workload K was provisioned for. **Guarantee B — continuous runtime attestation:** the process answering now is in a verified TEE state. TLS proves possession of K, not where K lives today: a key exfiltrated from a compromised guest, or a guest whose measurement drifted after release, still completes the handshake. A revocation at the KBS does not reach Hangar: a key stays acceptable to Hangar for as long as it is in the pin list, whatever the KBS has since decided. The issuer-side mitigations are short-lived keys and re-release tied to re-attestation; the Hangar-side control is the pin list itself.

**A pin-list change reaches every replica through the fleet projection.** Three rules make it safe:

- **The update writes only what it changes, and never a stale row.** Today the update handler saves a snapshot of the replica's whole local copy (`application/commands/crud_handlers.py:257-270`), so a replica whose copy is behind can write a removed pin back. For a `tls` or endpoint change the handler instead reads the row, applies only the fields the command carries, and writes with compare-and-set on a row version, refusing a write against a version it has not seen; the aggregate changes only after the write succeeds. A removed pin can therefore not be brought back by a concurrent update on another replica.
- **Every replica, including the one that handled the update, replaces its copy.** The update records `McpServerUpdated` after the row is written (`crud_handlers.py:270-274`), and it is persisted and tailed like any aggregate event. The fleet projection subscribes to it and, when the row's `tls` block or endpoint differs from the configuration the local copy's client was built with, builds a `COLD` copy from the row (`server_from_snapshot`) and puts it in the local fleet in place of the old one. The displaced copy is retired: it refuses `ensure_ready` and calls, and the replica's background worker closes its client and GET stream, so the projection itself publishes nothing and does no I/O beyond the row read, as `HandlerKind.PROJECTION` requires. This differs from a registration, which never replaces a running copy (`fleet_projection.py:131-135`), because an attested server's pins are the one part of its configuration that must not wait for a restart. The replica that handled the update compares against the built client, not against its in-place-updated aggregate, so its own pooled connections are not left on the old list.
- **An unreadable row fails closed.** Where the L7 precedent keeps the local copy when the row cannot be read (`fleet_projection.py:101-111`, `:161-166`), an attested server's copy is retired and its calls are refused until a later read succeeds, because the tail has moved past the event and would not deliver it again.

No new event type is needed. Exposure to a key that should no longer be trusted is therefore bounded by the time until the operator removes it from the pin list plus the event-tail delay to each replica, not by anything the KBS does. This bound is for servers registered through REST or the operator; a configuration-file server changes on each replica when that replica reloads its configuration (`application/commands/reload_handler.py`).

**`tls.max_connection_age` (default 1 h) caps the life of a connection.** httpcore has no maximum connection age, only an idle `keepalive_expiry`, so the cap is a scheduled replacement of the connection pool. It bounds how long one connection serves without a fresh handshake against its replica's current list; it does not replace the propagation above: every `max_connection_age` the `httpx.Client` inside the server's `HttpClient` is replaced, the old one is closed once its in-flight requests complete, and the MCP session (`_mcp_session_id`) is kept, because it lives on `HttpClient` and not on the pool. The streamable-HTTP GET stream, which has no read timeout and is the connection most in need of the cap, is closed and re-opened on the new pool.

### 3. Hangar is a relying party only through TLS; it is not a verifier

Hangar does not parse or verify Evidence, does not talk to an Attestation Service, holds no Endorsements or Reference Values, ships no attestation client, and does not evaluate X.509 chains for attested servers. The SPKI digest is computed with the `cryptography` package already in the dependency set (`pyproject.toml:70`). The domain stays free of platform SDKs.

### 4. Declaration and its carriage

**Config file.** The `tls` block gains `peer_identity` and `attested`:

```yaml
mcp_servers:
  payments:
    mode: remote
    endpoint: https://10.244.3.17:8443          # pod IP, Service name, anything: the name is not checked
    tls:
      attested: true
      peer_identity:
        key_ref: kbs:///default/payments/tls-key     # stable name of the key lineage; survives rotation
        spki_sha256:
          - sha256:9f2c...                     # current KBS-released key
          - sha256:4b10...                     # next key during rotation
      max_connection_age: 1h
```

A pin has one canonical form: `sha256:` followed by 64 lowercase hexadecimal characters, the SHA-256 of the DER-encoded `SubjectPublicKeyInfo`. Any other form (base64, uppercase, another algorithm) is refused at load and by the CRD pattern, so an encoding difference can never surface as a key mismatch.

Load-time refusals (`ConfigurationError` naming both halves, the #841/#902 pattern): `attested: true` on `mode: subprocess` or Hangar's own container mode (no connection to bind); with an `http://` endpoint; with an empty `spki_sha256` list, a pin not in canonical form, or no `key_ref`; with `verify_ssl: false` (meaningless, but a sign of a misread). `ca_cert_path` may be present for non-attested servers and is ignored for attested ones with a warning. The `http` block keeps the pins: building an HTTP client for a server declared attested without its pins raises instead of producing a client that verifies nothing.

**CRD.** `MCPServerSpec` gains `tls: {attested, peerIdentity: {keyRef, spkiSha256: []}, maxConnectionAge}`. SPKI digests are public values, so no Secret or ConfigMap reference is needed and the operator's least-privilege RBAC (`rbac_least_privilege_test.go:22-33`: no Secret reads) is untouched. CEL `XValidation` (`mcpdiscoverysource_types.go:31-32` precedent): `tls.attested == true` requires a non-empty `spkiSha256` whose items match the canonical pattern, and a `keyRef`. Once `MCPServerSpec` has `runtimeClassName`, an attested container-mode CR requires it; it is an operational precondition, not evidence: `gvisor` satisfies the rule and attests nothing. Remote-mode CRs need no runtime class. Because CRD CEL cannot read annotations and the image-digest policy is parameterised with a default of `warn`, a separate ValidatingAdmissionPolicy with an unparameterised `Deny` binding refuses `hangar.io/allow-mutable-image` on any CR with `tls.attested: true`, whatever `imageDigestPolicy` says and whether or not its ConfigMap exists.

**Carriage: operator to core is the only declaration path, and it does not exist today for container mode.** The operator registers only remote-mode CRs with core (`internal/controller/mcpserver_registration.go:222-224`, body `{mcp_server_id, mode, endpoint}`, `pkg/hangar/client.go:485`); container-mode pods reach core solely through core's own annotation discovery, which hardcodes `http://` (`server/bootstrap/discovery.py:235`) and skips unknown modes (`:186-196`); the REST create route reads no `tls` (`server/api/mcp_servers.py:319-360`) and `CreateMcpServerCommand` has no such field. This record therefore requires:

- (a) **the operator registers an attested CR before its pod exists.** It POSTs the name with the `tls` block and no endpoint; such a server cannot start until it has one. When the pod has an IP, the operator sets the endpoint; when the pod is deleted or rescheduled, the operator clears the endpoint before the old IP can be reused and sets the new one when the new pod has an IP. Because the name exists in core before any pod carries it, discovery never wins a race for it;
- (b) the REST create/update body, `CreateMcpServerCommand` and `UpdateMcpServerCommand` gain a `tls` field, the update gains `endpoint`, and create accepts an attested remote server without an endpoint; setting `tls` or the endpoint of an attested server requires `mcp_servers:attest` (§9). An endpoint set over REST is a HUMAN-provenance endpoint under the SSRF policy (ADR-021), so the pod CIDR must be in `ssrf.trusted_networks`; the operator and chart documentation say so, because a CR moved from discovery to attested registration meets the SSRF policy for the first time. An endpoint change on a server whose `key_ref` is unchanged resets that server's start backoff and circuit breaker, so failures against an old pod IP do not hold the new pod back;
- (c) the operator emits no discovery annotations for an attested CR, and core discovery never creates, replaces or downgrades a server whose name is in the attested-name record (§9). The check reads the shared store, not the replica's local fleet, because discovery runs on the lease holder (`server/bootstrap/discovery.py:54`); a refused name is logged as `discovered_attested_upstream_without_tls`;
- (d) `MCPDiscoverySource` sources with an attested `providerTemplate` are refused by the CEL for the source: the template is deep-copied into every server the source yields (`mcpdiscoverysource_controller.go:751-753`), so they would all share one `keyRef` and one pin list, which §7 forbids;
- (e) the operator registers an attested CR only with a core that advertises the capability, and only over an `https://` `hangar.url`; otherwise it reports the CR as not ready. A core that does not know the field would ignore `tls` in the REST body (`server/api/mcp_servers.py:342-360`), and its launcher reads only `verify_ssl` and `ca_cert_path` (`launchers/http.py:176-182`), so an attested declaration on an older core would be silently served as a plain one. The same holds for an older replica during a rolling upgrade: `McpServerConfigSnapshot.from_dict` drops keys it does not know (`domain/contracts/persistence.py:192-204`), so an older replica tailing the registration would rebuild the server without `tls`. Core therefore refuses an attested registration until every live instance in the fleet advertises the capability, and the upgrade note requires the whole fleet to run a core that knows the field before any server is declared attested. A configuration file that sets `attested` likewise requires a core that knows the key.

**Integrity of the declaration.** The SPKI list travels operator to core over `hangar.url` with `X-API-Key` (`pkg/hangar/client.go:582-583`); the chart's default `hangar.url` is empty and its documented example is plaintext (`helm-charts/.../values.yaml:177-180`). The declaration is public data; its integrity is what matters, and it is protected exactly as far as that channel is. The operator therefore refuses to register an attested CR over anything but `https://` (§4e), with the core's certificate verified against `hangar.tls.ca`. Delivery of the pin list to core is inside the trust model; delivery of calls to the pod is not.

### 5. Enforcement inside the handshake, before the first byte, fail-closed

**Where the check runs.** For a server with `tls.attested: true`, the client builds an `ssl.SSLContext` with `minimum_version = TLSv1_3`, `check_hostname=False` and `verify_mode=CERT_NONE` for chain purposes, and the check runs inside that context's handshake. TLS 1.3 binds the server certificate and its `CertificateVerify` to the handshake transcript and has no renegotiation, so the key checked is the key the channel was established with; an upstream that offers only TLS 1.2 fails the handshake. The context's `sslsocket_class` overrides `do_handshake`: it completes the handshake, reads the peer certificate (`getpeercert(binary_form=True)`, which returns the DER certificate under `CERT_NONE`), hashes its SPKI, keeps the digest on the socket for audit (§6), and raises when the digest is not in the pin list or no certificate was presented; it keeps the signature `do_handshake(self, block=False)`. Because the raised type is neither `OSError` nor `ValueError`, `SSLSocket._create` does not close the socket, so the override closes it before raising. The connection is therefore refused before the HTTP library returns it to the pool and before any request byte is written. httpcore's `trace` extension reports the end of `start_tls`, but only for a request that asked for it; the handshake route covers every connection, including the GET stream. Every upstream client is synchronous today (the only `AsyncClient` in core is `infrastructure/registry/client.py`); an asynchronous upstream path, if one is added, uses the same context with an `sslobject_class` that performs the same check. This is new TLS verification code in the transport (`http_client.py:425-495` area), merged with `_SsrfGuardedTransport` so there is one transport, and it applies to every new connection including retries, reconnects, pool replacement and the GET stream.

**What is refused and how it is coded.** Two outcomes are refusals, each with a bounded code and a dedicated exception type: `attested_upstream_key_mismatch` (the key is not in the list, or no certificate was presented) and `attested_upstream_plaintext` (the peer did not speak TLS, which the override recognises from the `ssl.SSLError` raised by `super().do_handshake()` and translates). Any other handshake failure (a reset, a timeout, a protocol error) stays the `OSError` it is, becomes httpcore's `ConnectError`, and is retried and recorded as a transport `error`, as today: a network blip is not a decision. The two refusal types derive from `ClientError`, not from `OSError`, so httpcore does not map them to `ConnectError`, and every aggregate I/O site that already handles `ClientError` (`mcp_server.py:2010, 2072, 2265, 2316, 2361, 2404`) handles them without letting an exception escape. They carry `failure_code` and `observed_peer_spki`.

**How the type survives each layer.**

- `HttpClient.call` (`http_client.py:816-827`) and `HttpClient.notify` (`:968`) re-raise `ClientError` subclasses unchanged instead of wrapping them, so a refusal on the connection that carries `notifications/initialized` is not turned into `start_failed`; `_post_with_retry` does not retry them; the executor's retry (`executor.py:2765`) does not retry them either.
- `McpServer` start re-raises them unwrapped, as it already re-raises `McpServerNotHereError` (`mcp_server.py:951-961`), still recording the failure with `_handle_start_failure` as that branch does, instead of wrapping them in `McpServerStartError` (`:969-985`). A caller waiting on that start in `ensure_ready` receives the stored exception itself, not a new generic `McpServerStartError` (`:917-921`).
- `_gate_cold_start` refuses them with the type's own name instead of the literal `McpServerStartError` (`executor.py:2558`), and as an expected refusal: no `record_handled_failure`, span UNSET, one `batch_call_refused` line.
- MCP session renegotiation (#1852, `_call_with_session_recovery`, `mcp_server.py:1307`) lets them through instead of turning them into an RPC error without a code.
- The GET-stream loop (`http_client.py:1035`) treats them as terminal for the current pool: it stops retrying, logs, and counts the metric; the stream is re-opened when the pool or the server is next replaced (§2).

`_GATE_REASONS` is keyed by the refusal's `error_type` string, which the gate sets (`executor.py:2908-2911`); the two types map to the two codes with outcome `deny`, not `error`. ADR-029 §5 already requires a bounded code list per gate, defined next to the gate; adding these codes extends that list and does not amend ADR-029.

**Cold and warm agree.** On a `COLD` or `DEAD` server the first contact happens in `_gate_cold_start` (`executor.py:2512`), which records the gate decision with the specific reason and publishes the `ToolCallRefused` that every gate refusal publishes. On a warm server the refusal is a `ToolInvocationFailed` with `failure_code`, and the two types join `_REFUSED_AT_DISPATCH` (`executor.py:147`) so `hangar.call.outcome` is `refused` and the span is UNSET, as on the cold path. For a group, a member's refusal counts as that member's failure and selection moves on, as a member's failed start does today. A refusal counts as a failed start for backoff and the circuit breaker, like any failed start; the refusals that follow it keep their own reasons (`not_revived_by_calls`, `circuit_open`), the server's last start error is the refusal, and an endpoint change resets both (§4b). No new entry in `_GATES`.

### 6. Audit, from the socket, with explicit semantics

`ToolInvocationCompleted` and `ToolInvocationFailed` gain optional `upstream_peer_spki: str | None`; `ToolInvocationFailed` gains `failure_code: str | None` (default `None`, so stored events read back unchanged); and `ToolInvocationFailed` and `ToolCallRefused` gain optional `observed_peer_spki`, so the observed key is kept on the cold-start path too. The value is the digest the handshake kept on the socket of the connection that served this attempt, read through `response.extensions["network_stream"].get_extra_info("socket")` before the body is consumed — not `get_extra_info("ssl_object")`, which is gone once the server closes the connection — and never from configuration, so a retry on a different connection records that connection's key and a group member's key is never attributed to a call another member served.

| Case | `upstream_peer_spki` | Other fields |
| --- | --- | --- |
| Refusal before any connection | absent | — |
| Transport failure (reset, timeout, protocol error) | absent | recorded as today |
| Plaintext peer | absent | `failure_code` or the refusal's reason `attested_upstream_plaintext` |
| Key mismatch or no certificate | absent | `observed_peer_spki` set when a certificate was presented |
| Verified connection, call succeeded or failed at the application level | the verified key | — |

Exporters JSON/CEF/LEEF/syslog carry the field next to `caller_id`; spans carry `hangar.upstream.peer_spki`. `mcp-hangar why` already reads the `ToolCallRefused` a cold-start refusal publishes; it is extended to read `ToolInvocationFailed` rows whose `failure_code` is one of the two codes (`refusal_log.py:26-32` today lists five refusal types and no invocation failures), and prints expected pins and observed key for both. It does not synthesise a `ToolCallRefused` for a warm refusal. Metric: `mcp_hangar_attested_upstream_connections_total{server, outcome}`, registered in `_register_all_metrics()` (#1059), counting every handshake of an attested server, including the GET stream's.

### 7. The upstream identity of an attested server is its key lineage

`McpServer.upstream_identity()` returns `attested:<key_ref>` for a server with `tls.attested: true`, instead of `remote:<scheme>://<host>:<port>`. The identity must be the same on every replica and stable across a rotation, and it must be computable from configuration so that a server that has never connected has it too. A value taken from the connection, or derived from the pin list, fails this: the list changes when the next key is added and again when the old one is dropped. `key_ref` is the operator's stable name for the key lineage, so a rescheduled attested pod with a new IP keeps its digest pins, and a key rotation keeps them too. Nothing is lost by not binding to the key itself: a key outside the pin list is refused at connect (§5) before any tool is served. Changing `key_ref` is a different upstream, and its pins are recorded again. Declaring an existing server attested changes its identity the same way, so all its digest pins are recorded again; the upgrade note says so.

Because `key_ref` is a label the declarer chooses, two rules keep it from carrying pins it should not. `key_ref` is unique across servers, enforced by the attested-name record in the shared store (§9), not by a replica's local fleet, so two replicas registering concurrently cannot both succeed. A single update whose pin list shares no key with the stored list must change `key_ref` or is refused; for a configuration-file server the stored list is the persisted row, and a server with no row has no previous list. A stepwise replacement through an intermediate list (`[A]` → `[A, X]` → `[X]`) passes this rule: it is a rotation by construction, and the holder of `mcp_servers:attest` is a trust root either way (§9b). The rule stops an accidental wholesale swap, not a deliberate one. Non-attested servers are unchanged.

### 8. What "attested" means in Hangar's vocabulary

`tls.attested: true` means: every connection to this server must terminate at a key whose SPKI is in the declared list, and the operator declares that those keys were released by a KBS only after attestation of the workload they were provisioned for (Guarantee A). Hangar verifies the key, not the attestation evidence. The declaration does not establish continuous runtime attestation, current measurements, code integrity, or protection against key extraction after release. Audit records distinguish the configured pins from the key observed on the connection; no observed key is recorded when no verified connection was established. Documentation keeps three things apart: build provenance of Hangar's artefacts; the digest of a tool's contract; the attested-issuance key of an upstream connection.

### 9. Permission, the attested-name record and trust roots

A new permission `mcp_servers:attest`, held by `kubernetes-operator` and `admin` only, is required to set `tls.attested` or `peer_identity`, to change the endpoint of an attested server, to delete one, and to create a server under a name in the attested-name record. `mcp_servers:write` and `mcp_servers:lifecycle`, which `developer` holds (`auth/roles.py:197-203`; delete needs `lifecycle`, `server/api/mcp_servers.py:419`), are not enough for any of these. The check sits in the command handlers, not in the REST routes, so every path that creates or changes a server is covered: REST, `hangar_load` (which needs only `mcp_servers:write`, `server/tools/tool_permissions.py:94`), discovery approval (`hangar_approve`) and core discovery itself.

**The attested-name record.** The configuration store keeps one record per name ever declared attested, with its `key_ref`, in its own table (`attested_names(name PRIMARY KEY, key_ref UNIQUE)`), because deleting a server removes its configuration row. The record is written in the same transaction as the configuration row (`TransactionalMcpServerConfigRepository`, `infrastructure/persistence/unit_of_work.py:20`), with an insert that does nothing on conflict followed by a check of the existing row, which behaves the same on SQLite and PostgreSQL ([ADR-019](ADR-019-one-storage-decision-two-backends.md)); a configuration-file server loaded on every replica writes the same pair idempotently, and a failed write refuses the attested server rather than serving it. The record survives the deletion of the server and is removed only by a holder of `mcp_servers:attest`. On a shared backend every replica reads it from the shared store, so it survives restarts and is the same on every replica. An in-memory repository has no projection and no tail (`server/bootstrap/event_handlers.py:202-203`, `server/bootstrap/coordination.py:142-152`) and keeps nothing across a restart, so declaring a server attested over REST or from the operator is refused there. It is what keeps a deleted attested server from being re-created as a plain one, what keeps discovery off an attested name (§4c), and what makes `key_ref` unique (§7). The config file remains operator-trusted ([ADR-021](ADR-021-config-file-endpoints-outside-the-ssrf-policy.md)).

Trust roots, named:

- (a) the KBS operator and its reference values;
- (b) whoever holds `mcp_servers:attest` or writes the config file — they can pin a key they control, so this is operator-declared trust, not independently administered trust, and the audit record says what the operator declared, not what a third party verified;
- (c) the guest TCB after key release — a compromised guest can exfiltrate K;
- (d) the operator-to-core channel for the integrity of the pin list (§4);
- (e) write access to the shared configuration store and the event store, which hold the pins, the attested-name record and the rows every replica rebuilds from.

Independently administered trust (a core-side pin store the registrant cannot write) is a later decision and is not made here.

### 10. Defaults, compatibility, naming

No behavioural change for servers without `tls.attested: true`; existing TLS behaviour, including the `verify_ssl: false` warning (`launchers/http.py:196-210`), is untouched. The fleet snapshot carries no `tls` today (`fleet_snapshot.py:27-76`, `:124-178`): a server rebuilt from it on restart or on a peer replica would come back without `attested` and without pins and be served as a plain one. `McpServerConfigSnapshot` therefore gains the `tls` block (it holds no secret), `server_from_snapshot` restores it, and a row whose `tls.attested` cannot be restored is refused, not rebuilt as a plain server. Additive CRD fields, no API version bump. `McpServer.provenance` (`HUMAN | DISCOVERY`) keeps its SSRF meaning (ADR-021). Nothing here is named attestation result, measurement or verifier.

The change spans config and validation; a new transport verification path and its propagation through the start, call, renegotiation and stream paths; the registration body, command and REST fields; the fleet snapshot, versioned writes and the projection of `McpServerUpdated`; the attested-name table on both backends; the operator's registration flow and capability check; one admission policy; discovery refusal; event schema and exporters; `why`; one metric; one permission; the tests below.

## Consequences

### Positive

- A call to a declared server is carried by a connection that provably ends at one of the operator's pinned keys, verified before any byte is sent, and the audit record names the key read from the socket — a claim Hangar can stand behind, unlike a verifier result with a shelf life or a CA-anchored name whose meaning lives in an issuance policy Hangar cannot see.
- No new gate in `_GATES`, no new event type, no verifier client, no CA handling, no Secret reads in the operator. The trust root shrinks to "who may write the pin list".
- Nothing changes for servers that do not declare `tls.attested: true`.

### Negative

- The KBS operator and its reference values are a trust root of Hangar's audit trail. A KBS policy that releases a leaf key to the wrong workload makes that server's "attested" records meaningless, and Hangar cannot detect it.
- Operator-declared trust only: whoever holds `mcp_servers:attest` or writes the config file can pin a key they control. The record names it and narrows it (`developer` cannot), but does not close it; independent administration is a later decision.
- Guarantee A, not B: a key exfiltrated from a compromised guest or a guest whose measurement drifted after release keeps working against Hangar until the operator removes it from the pin list; a revocation at the KBS alone changes nothing on Hangar's side. Documented; not solvable on Hangar's side without RA-TLS.
- The pin list's integrity depends on the operator-to-core channel and on the shared stores. The operator refuses plaintext `hangar.url` for attested CRs, but the stores remain a trust root.
- A declared server whose key is not in the list is unavailable, fail-closed, with no "temporary" plaintext mode. Rotation requires the operator to publish the next key before switching; a missed step takes the upstream down. A pin-list change stops the server to `COLD` on every replica.
- Upstreams must serve TLS 1.3 with the KBS-released key at start-up (CoCo CDH supports resource retrieval; serving TLS with it is integration work on the upstream image, outside Hangar).
- Declaring an existing server attested re-records all of its digest pins.
- An attested server needs a shared, durable backend and a fleet upgraded as a whole before the first declaration.
- New operator work: registration before the pod, endpoint maintenance across reschedules, the capability and `https://` checks, one admission policy, and the dependency on `runtimeClassName`. New core work: transport verification and its propagation, event fields, the fleet snapshot and projection, the attested-name record, `why`, permission, REST/command fields.
- Three things a reader will call "attestation" must stay apart in every document: build provenance of Hangar's artefacts, the digest of a tool contract, the attested-issuance key of an upstream connection.

### Neutral

- Every acceptance test except T26 runs without hardware (a self-signed leaf, a local TLS server, envtest); no security statement may rest on a run without a TEE, and the documentation must say so.
- The verifier-result design is rejected in the form described in Alternative 1; a design with a different binding would need its own record.
- Hangar-in-TEE (Alternative 5) remains possible as a separate record.

## Alternatives Considered

### 1. Verifier result as a verdict input with TTL

- **Rejected**: Hangar would consume an Attestation Result (EAT) from Trustee AS, bound to `upstream_identity()`, with `maxAge`, a new `_gate_attestation` in `_GATES`, an `AttestationResultRecorded` event in `pin_ledger`, persistence on the fleet snapshot and propagation via the event tail. The defects that decide it: (a) for operator pods `upstream_identity()` is `remote:http://<pod_ip>:<port>`, so the binding is to an IP the CNI reuses and the snapshot/replay machinery is dead weight; (b) with TTL and no channel binding, a pod-create attacker who inherits the IP inside `maxAge` receives calls audited as `attestation_status=ok`, a claim Hangar could not stand behind; (c) verification as a `PROJECTION` handler on `McpServerStarted` violates `HandlerKind` (network I/O, publishes), and as an `EFFECT` it runs once per replica because every replica emits `McpServerStarted`; (d) a `_GATES` entry cannot govern prompts/resources or group listings, which are decided elsewhere (`is_governed_allowed`, `fastmcp_server/flat_tool_projection.py:235`); (e) `referenceValues[kind=image-digest]` is not something an SNP/TDX verifier attests.

### 2. KBS-only: the attested guest gets its downstream credential from the KBS, Hangar is unchanged

- **Adopted as the baseline, insufficient on its own**: §1 preserves it. It gives no channel binding: Hangar still dials an IP and cannot tell an attested pod from one that inherited its address, and the audit trail cannot say which it was. The decision adds exactly one thing: the KBS also releases the upstream's TLS leaf key, and Hangar pins its SPKI.

### 3. CA-anchored identity: pin an issuer CA and match a SAN

- **Rejected**: three independent defects. A CA private key released to guests lets any admitted guest mint any name; a CA kept at an issuer makes the SAN a statement of an issuance policy Hangar cannot inspect, so `peer_identity.san` would mean whatever the issuer's rules mean; and the client's hostname verification (`sni_hostname`, `http_client.py:267-270`; CPython matches DNS/IP SANs only) rejects a URI SAN and cannot match a static leaf against a CNI-assigned pod IP. SPKI pinning (§2) needs no chain, no name and no issuance policy on Hangar's side, and shrinks the trust root to "who may write the pin list". Cost: rotation is a pin-list change, and the operator must read the SPKI from the KBS resource it provisioned.

### 4. Sidecar or mesh mTLS termination with SPIFFE policy, Hangar untouched

- **Not chosen; compatible for enforcement, loses the audit field**: a mesh that terminates mTLS beside the upstream and admits only SVIDs gated on attestation enforces the same property without any Hangar change; Hangar then sees plaintext to a local sidecar and cannot record which key answered. A deployment that already runs such a mesh may prefer it; this record does not stand in its way and does not claim its audit guarantees for it.

### 5. Hangar itself in a TEE, policy measured, log signed by an enclave key

- **Rejected**: it changes the product from a fleet-level policy enforcement plane into an attested single-process gateway — the same widening-under-pressure that ADR-010 refused for SaaS. It needs an attestation provider abstraction, key release, freshness and rollback protection for Hangar's own log. HA (ADR-020) assumes N replicas over one log; enclave-held signing keys per replica need either a migratable sealed key or N keys and a verifier that knows them. Nothing here forbids a later record on it; it must supersede this clause explicitly.

### 6. Hangar issues the nonce and verifies Evidence

- **Rejected**: MCP has no in-band channel from an intermediary to the upstream's Attestation Agent; a nonce would travel out of band (`_meta`, a header), which is a protocol change under discussion elsewhere, not a Hangar change. SNP/TDX quote verification in core duplicates Trustee and Veraison and brings platform cryptography into the domain.

### 7. RA-TLS (X.509 with the quote in an extension) to the upstream

- **Deferred**: it is the stronger form of §2: the client verifies the quote inside the handshake rather than trusting a KBS-gated key release. It needs an RA-TLS-aware client and a verifier at handshake time. The KBS-brokered form chosen here gives the same channel-binding property with the client Hangar already has, at the cost of trusting the KBS operator (§9a). If an upstream ecosystem standardises RA-TLS, a record can add it as a second `peer_identity` kind without touching anything else.

### 8. OPA-only: the fact in context, policy in Rego

- **Rejected**: OPA authorization for `hangar_call` runs before target resolution and with an empty context (`server/tools/batch/__init__.py:245`, ADR-028 §2); filling it would mean restructuring `_authorize_calls` to run after resolution, which is an ADR-028 amendment, and OPA is optional, so an installation without it would have no enforcement at all. Connect-time enforcement works in every configuration.

### 9. SPIRE with a TPM/TEE node attestor issuing SVIDs

- **Not chosen; compatible under a condition**: a SPIRE-issued SVID is a key like any other; if the operator pins its SPKI, nothing in §2 changes. Two caveats: SPIFFE/SPIRE is compatible only when SVID issuance is gated by an attestation policy that satisfies the declared trust model — a TPM node attestor proves the node booted a measured stack, not that this process runs in a TEE, and plain SPIRE with `attested: true` would claim more than the environment provides; and SVID rotation is frequent, so the pin list must be fed from the SPIRE trust bundle or the deployment must pin the SPIRE CA instead — which is Alternative 3 with its SAN problems. The record keeps SPKI pinning as the only mode and lets SPIRE deployments decide whether the rotation cost is acceptable.

### 10. Admission-time-only verification (Kata policy hash gates the KBS; Hangar unchanged)

- **Insufficient alone**: same reason as Alternative 2. It secures what runs; it does not bind what Hangar dials to what runs.

### 11. Attestation declared on MCPServerGroup

- **Rejected**: the connection is per upstream; a group is a projection over members and a declaration there would have to be fanned out — the key-mismatch class of #1036/#1040. A group may contain attested and non-attested members; each member's `tls` block decides.

### 12. A new CRD API version for the new fields

- **Rejected**: `tls` is additive and optional; absent means today's behaviour. Optional fields added to a served version are backward compatible for existing objects and clients, which is all an API version bump would buy.

### 13. Defer the decision until a deployment asks

- **Rejected**: deciding the contract before a deployment depends on it keeps that deployment from re-deriving it under pressure.

### 14. Propagate pin-list changes only through replica restarts

- **Rejected**: a removed key would stay acceptable on every replica that has not restarted, with no bound at all. The fleet projection already applies L7 policy on every replica; applying `McpServerUpdated` the same way bounds the window by the event tail.
